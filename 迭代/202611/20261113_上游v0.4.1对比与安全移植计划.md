## 4. 本地分叉与冲突判断

### 4.1 本地已有的相关能力

- `upstream_proxy`：显式出站代理，空值强制直连，不复用环境代理；
- `lifecycle`：控制面与转发数据面分离；
- `process`：单实例锁、进程身份和端口归属校验；
- 配置 `revision` 和 409 冲突保护；
- 规则描述、重置、导出、导入和非法正则校验；
- 管理令牌使用 `localStorage`，支持 `?token=` 和 `sessionStorage` 迁移；
- 本地规则集构建位于 `crates/veil/src/proxy/forward.rs`。

### 4.2 不能整包应用的原因

完整上游补丁在以下文件存在冲突或语义差异：

```text
Cargo.lock
Cargo.toml
crates/veil-engine/src/builtin.rs
crates/veil/src/admin/api.rs
crates/veil/src/config.rs
crates/veil/src/main.rs
crates/veil/src/proxy/forward.rs
crates/veil/tests/admin_api.rs
ui/src/App.tsx
ui/src/api.ts
ui/src/i18n.tsx
ui/src/style.css
```

主要冲突点：

1. 本地已有 `upstream_proxy`，上游新增 `[egress]`，存在配置模型重复；
2. 本地规则构建在 proxy 层，上游新增独立 `ruleset.rs`；
3. 本地令牌使用 `localStorage`，上游改为登录页和 Cookie；
4. 本地管理 API 带 `revision`、规则描述等定制字段；
5. 上游新增的默认 region pack 和头部改写会改变现有请求行为。

因此本计划只做选择性移植，不进行整分支覆盖。

## 5. 逐项评估

### 5.1 P0：Base64 / 多模态数据保护

**结论：已实施并提交；P0 测试通过。**

#### 实施状态（2026-11-13）

P0 已包含在提交 `b1a89da`：

| 文件 | 修改用途 |
| --- | --- |
| `crates/veil-engine/src/binary.rs` | 识别 data URL、标准/URL-safe Base64，并用无分配结构校验减少误判 |
| `crates/veil-engine/src/lib.rs` | 导出 `binary` 模块 |
| `crates/veil-engine/src/walk.rs` | 传递 JSON 字段上下文，对多模态 `data` 和 data URL 跳过脱敏，普通文本继续扫描 |
| `crates/veil/src/proxy/forward.rs` | 非 JSON body 命中 Base64 规则时原样转发 |
| `crates/veil/tests/proxy_core.rs` | 增加多模态 JSON 和原始 Base64 body 集成测试 |

验证结果：

- `cargo test -p veil-engine`：50 passed；
- `cargo test -p veil`：82 passed；
- 覆盖 Anthropic `source.data`、OpenAI data URL、URL-safe Base64、长普通文本反例和原始 Base64 body。

#### 实施前风险

P0 实施前，本地 `crates/veil-engine/src/walk.rs` 只把字符串内容传给脱敏函数，不携带 JSON key 上下文：

```rust
map_string_values(value, &mut |text| {
    desensitize_string(text, rules, store, creator)
})
```

P0 实施前，本地 `crates/veil/src/proxy/forward.rs` 对非 JSON body 会把整段内容作为文本扫描。

因此以下内容可能被手机号、IP、Token 等规则误改：

- Anthropic `source.data`；
- OpenAI `image_url.url`；
- `data:image/...;base64,...`；
- 音频、视频、文件 Base64；
- 其他长 Base64 二进制字段。

Base64 中任意字符被替换后，整个 payload 可能无法解码，表现为上游 400、图片损坏或请求失败。

#### 实施内容

1. 新增 `crates/veil-engine/src/binary.rs`：
   - `is_data_url_base64`；
   - `looks_like_base64_blob`；
   - `should_skip_desensitize(key, text)`；
   - 对应单元测试。

2. 修改 `crates/veil-engine/src/lib.rs`：
   - 导出 `binary` 模块。

3. 修改 `crates/veil-engine/src/walk.rs`：
   - `map_string_values` 增加 `Option<&str>` 字段上下文；
   - 识别 Anthropic 的 `type == "base64"` 或 `media_type` 为 `image/`、`audio/`、`video/` 的对象；
   - 对匹配对象中的 `data` 字段跳过脱敏；
   - `restore_json` 保持原有恢复行为，不对 Base64 做额外改写。

4. 修改 `crates/veil/src/proxy/forward.rs`：
   - 非 JSON body 若被判定为 data URL 或纯 Base64，则原样转发；
   - JSON body 继续通过 `desensitize_json`，由字段上下文判断。

#### 与上游实现的差异

上游的 `looks_like_base64_blob` 允许空格和换行，并对超过 200 字符的字符串较宽松，可能把长普通英文文本误判为 Base64。本次实现采用更严格的无分配结构校验：

- `data:` URL 直接识别；
- 明确的二进制字段优先跳过；
- 通用字段仅在字符集、长度、空白、padding 和结构满足条件时跳过；
- 标准 Base64 与 URL-safe Base64 字符不能混用；
- `data` 等二进制提示键仍要求内容通过 Base64 结构校验，普通文本继续扫描；
- 增加“长普通英文文本不能被跳过”的反例测试。

#### 用途与收益

- 保护多模态请求中的图片、音频和文件内容；
- 避免脱敏规则破坏 Base64；
- 保持普通文本、代码和 JSON 文本字段的脱敏能力；
- 降低上游 400 和请求失败率。

#### 影响与取舍

- 被判定为不透明 Base64 的内容不会再扫描内部敏感字符串；
- 这是有意的兼容性取舍，必须写入测试和文档；
- 普通文本、短字符串和明确可读内容继续按原规则扫描；
- 不影响响应恢复流程；
- `data` 字段仅在内容符合 Base64 结构时跳过，避免把普通短文本当作二进制；
- 该行为是脱敏核心的唯一二进制载荷例外，普通可读字符串仍按原规则扫描。

#### 验收结果

- `cargo test -p veil-engine`；
- `cargo test -p veil`；
- Anthropic `source.data` 图片保持不变；
- OpenAI `image_url.url` 的 data URL 保持不变；
- URL-safe Base64 不被 `sk-` 规则误改；
- 同一请求中的手机号、IP 仍被脱敏；
- 长普通英文文本不被误判；
- 代理集成测试断言转发后的 Base64 与原始请求一致。

```rust

.or_else(|| headers.get("x-dgw-admin-token"))
```

- 增加 `Authorization: Bearer <token>` 提取；
- 保持现有认证优先级：
  1. `x-veil-admin-token`
  2. `x-dgw-admin-token`
  3. `Authorization: Bearer <token>`
  4. `veil_admin` Cookie
  5. `dgw_admin` Cookie

#### 用途与收益

- 修复旧客户端兼容；
- 让标准管理客户端可以使用 Bearer；
- 不改变当前 UI 的 `x-veil-admin-token` 调用方式；
- 不改变数据面转发逻辑。

#### 影响与风险

- 只是扩大管理接口可接受的认证入口；
- 管理端口仍然要求有效令牌；
- 不同时移植上游登录页和 Cookie 写入流程，避免形成多套认证状态；

### 5.3 P2：地区规则包、请求头改写与 egress 代理

**结论：暂不实施。**

#### 不直接移植的原因

1. 上游默认 `packs.region = true`，会让现有配置在升级后自动改写 `Asia/Shanghai`、`zh-CN` 等内容。
2. 上游默认 `headers.profile = "region_neutral"`，会改写每个上游请求的 `Accept-Language`。
3. 上游新增 `[egress]`，与本地已有的 `upstream_proxy` 重复。
4. 上游新增独立 `ruleset.rs`，与本地 `ruleset_from_config` 和规则管理流程重叠。
5. 这些改动属于产品策略变化，不只是安全修复，不能默认开启。

#### 未来如需要，必须满足的设计约束

- 地区规则包默认关闭；
- 请求头 profile 默认 `passthrough`；
- 复用本地 `upstream_proxy`，不增加第二套代理字段；
- 保留本地空代理强制直连语义，不能在空值时隐式继承环境代理；
- SOCKS5 只作为独立可选能力，增加 `reqwest` 的 `socks` feature 后单独测试；
- 规则包逻辑接入本地 `ruleset_from_config`，不复制上游的规则构建管线；
- 所有行为变更必须有显式开关、迁移说明和回滚路径。

#### 本次结论

保持当前 `upstream_proxy`、现有规则集和现有请求头行为不变。
