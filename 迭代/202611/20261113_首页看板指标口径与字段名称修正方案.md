# 首页看板字段标题、范围与说明文字修正方案

> 文档类型：看板信息表达与术语修正方案  
> 日期：2026-11-13  
> 状态：P0 已实施并通过测试；P1 延后，等待后续需求  
> 适用版本：本地 Veil `v0.3.17` 之后  
> 本轮范围：仅看板前端展示、标题、单位、范围、说明文字和状态文案  
> 不改范围：后端缓存容量、累计计数、窗口聚合、API 数据模型、SQLite 历史存储  
> 关联代码：`ui/src/pages/Dashboard.tsx`、`ui/src/i18n.tsx`、`ui/src/api.ts`

## 1. 本轮决策

本轮不把“累计请求数”“完整 20 分钟聚合”或“全历史查询”作为前置任务，而是先把现有数据真实、完整地表达出来。

P0 必须做到：

1. 每张卡片都直接显示统计范围和单位；
2. 页面上不再出现无范围的“请求”“错误”“延迟”“SSE”等标题；
3. 统一使用“脱敏”“脱敏请求”“脱敏命中”“缓存内”“上游首包”等术语；
4. 明确 512 条缓存已满时会发生滚动淘汰；
5. 明确柱状图基于缓存计算，缓存覆盖不足 20 分钟时可能不完整；
6. 明确平均延迟只代表上游首包，不代表完整响应耗时；
7. 修正服务状态、图表标签、加载、空数据和错误状态；
8. 中英文文案同步修改。

P0 不改变任何统计值，只改变用户对统计值的理解。

## 3. 现状问题

| 当前展示 | 当前实际含义 | 用户容易产生的误解 |
| --- | --- | --- |
| 请求 | 最近 512 条缓存的事件数 | 以为是累计请求数，或以为数据停止更新 |
| 打过码 | 最近 512 条中有脱敏命中的请求数 | 以为是脱敏命中次数 |
| 出错 | 最近 512 条中状态码大于等于 400 或带错误类别的事件数 | 以为覆盖了所有失败请求 |
| 平均延迟 | 最近 512 条中收到上游响应头的时间均值 | 以为是完整响应耗时 |
| 2xx | 最近 512 条中的 2xx 事件数 | 不知道范围 |
| SSE | 最近 512 条中的流式响应数 | 不知道是缓存值，也可能不理解 SSE |
| 近 20 分钟请求 | 前端从最近 512 条缓存中分桶 | 不知道高流量时可能因缓存不足而少算 |
| 打码类型 | 最近 512 条缓存内的命中次数 | 误以为和近 20 分钟图使用同一时间范围 |

## 4. 统一术语

| 术语 | 定义 | 禁止或避免使用 |
| --- | --- | --- |
| 请求 | 一条进入流量记录的请求事件 | 单独使用“请求”且不写范围 |
| 缓存内 | 当前内存中保留的最近最多 512 条事件 | “实时全部”“全部请求” |
| 脱敏 | 敏感值被规则匹配并替换为占位符 | 打码、化名、混淆混用 |
| 脱敏请求 | 至少命中一次规则的请求 | 打过码 |
| 脱敏命中 | 规则实际匹配并替换的次数；一个请求可以命中多次 | 打码次数 |
| 上游首包 | 从请求开始到收到上游响应头的时间 | 平均延迟、总耗时 |
| 流式响应 | `Content-Type` 包含 `text/event-stream` 的响应 | 只写 SSE 且无解释 |
| 成功响应 | 最终状态码为 2xx 的响应 | 只写 2xx 且无解释 |
| 错误请求 | 缓存中状态码大于等于 400 或带错误类别的请求 | 全量错误、所有失败 |
| 缓存已满 | 事件数达到 512，后续事件会淘汰最旧记录 | 请求数上限、总数到顶 |

## 5. 页面信息结构

建议把看板分成三个清晰区域。

### 5.1 顶部数据范围条

在标题下方、服务控制上方增加一行数据范围说明：

```text
数据范围：缓存内最近 512 条事件 · 更新于 14:25:06 · 每 2 秒刷新
```

缓存满时追加状态标签：

```text
缓存已满，旧事件会滚动淘汰
```

缓存未满时显示：

```text
缓存 320 / 512 条
```

### 5.2 缓存指标区

标题：

```text
缓存指标（最近 512 条事件）
```

该区域放置：

- 缓存内请求数；
- 缓存内脱敏请求数；
- 缓存内错误请求数；
- 缓存内上游首包均值；
- 缓存内成功响应；
- 缓存内流式响应。

### 5.3 时间窗口区

标题：

```text
时间窗口指标
```

该区域放置：

- 近 20 分钟请求趋势图。

说明：

```text
每柱 1 分钟 · 最近 20 分钟 · 基于缓存内事件计算
```

如果当前缓存最旧事件距现在不足 20 分钟，显示：

```text
当前缓存仅覆盖最近 X 分钟，更早部分可能不完整
```

### 5.4 脱敏分布区

标题：

```text
缓存内脱敏类型
```

说明：

```text
单位：命中次数 · 范围：最近 512 条缓存事件 · 与近 20 分钟图口径不同
```

不要把脱敏分布和 20 分钟趋势图并列成同一统计范围，除非标题已经明确写出各自范围。

## 6. 卡片字段设计

所有卡片必须在可见文字中同时展示范围或单位，不能只依赖悬停提示。

| 卡片标题 | 主值示例 | 单位 | 可见范围说明 | 说明文字或提示 |
| --- | --- | --- | --- | --- |
| 缓存内请求数 | `512` | 条 | 最近 512 条事件 | 缓存已满，旧事件会滚动淘汰 |
| 缓存内脱敏请求数 | `436` | 个请求 | 最近 512 条事件 | 至少命中一次规则的请求；不是命中次数 |
| 缓存内错误请求数 | `40` | 个请求 | 最近 512 条事件 | 状态码大于等于 400 或带错误类别的已记录事件 |
| 缓存内上游首包均值 | `5,146` | ms | 最近 512 条事件 | 收到上游响应头的时间；不含响应体传输和还原 |
| 缓存内成功响应 | `472` | 个响应 | 最近 512 条事件 | 最终状态码为 2xx |
| 缓存内流式响应 | `459` | 个响应 | 最近 512 条事件 | `Content-Type` 包含 `text/event-stream` |
| 近 20 分钟请求趋势 | 柱状图 | 条/分钟 | 最近 20 分钟 | 每柱 1 分钟；基于缓存，覆盖不足时显示提示 |
| 缓存内脱敏类型 | 类型与次数 | 命中次数 | 最近 512 条事件 | 与近 20 分钟图口径不同 |

## 7. 页面级说明文字

### 7.1 看板帮助文案

中文：

```text
本页缓存指标来自本机最近 512 条流量事件，每 2 秒刷新。缓存满后旧事件会滚动淘汰。近 20 分钟趋势基于同一份缓存计算，缓存覆盖不足时可能不完整。脱敏请求数与脱敏命中次数含义不同。
```

英文：

```text
Cached metrics use the latest 512 traffic events in memory and refresh every 2 seconds. Older events are evicted when the cache is full. The 20-minute trend uses the same cache and may be incomplete when coverage is shorter. A request with at least one redaction is different from a redaction occurrence.
```

### 7.2 口径说明

建议增加“口径说明”折叠区或提示按钮，至少包含：

- 缓存指标范围：最近 512 条事件；
- 脱敏请求：至少命中一次规则的请求；
- 脱敏命中：规则实际替换次数，一个请求可以多次命中；
- 上游首包：收到上游响应头的时间；
- 错误请求：已记录事件中状态码大于等于 400 或带错误类别；
- 成功响应：2xx；
- 流式响应：SSE / `text/event-stream`；
- 时间窗口：近 20 分钟，受缓存覆盖范围限制。

### 7.3 服务状态文案

不再直接显示英文枚举值。

| 后端值 | 中文 | 英文 |
| --- | --- | --- |
| starting | 启动中 | Starting |
| running | 运行中 | Running |
| stopping | 停止中 | Stopping |
| stopped | 已停止 | Stopped |
| degraded | 降级运行 | Degraded |

状态行改为：

```text
数据面：运行中 · 控制面：运行中 · 进程 ID：22684 · 数据面监听端口：18787, 18791, 18792
```

不再使用无说明的 `forwarding`、`running` 或裸端口列表。

## 11. 风险与回滚

| 风险 | 处理 |
| --- | --- |
| 文案过长影响卡片布局 | 使用短标题加两行说明，完整定义放入口径说明 |
| 用户仍把缓存指标当累计值 | 标题、数量单位和说明三处同时写“缓存内” |
| 20 分钟趋势数据不完整 | 显示覆盖分钟数和“可能不完整”提示 |
| 术语变化影响旧用户理解 | 在口径说明中保留“SSE”技术名称，并解释脱敏含义 |
| 前端错误状态改变范围过大 | 只调整看板错误处理，不改 API 和代理链路 |
| 文案修改与 UI 测试不同步 | 同步更新中英文键和 Dashboard 测试 |

回滚方式：

- P0 仅涉及前端文案、布局和错误状态；
- 回滚前端即可恢复旧展示；
- 不影响代理、配置、缓存、SQLite 和流量采集。
