### 4. 本地迭代的主要方向

当前本地版本相比 `yuan-veil v0.3.14`，主要沿以下方向迭代：

1. **运行可控性**：控制面与转发数据面解耦，支持启动、停止、重启和退出。
2. **进程安全**：增加单实例锁、运行元数据、进程身份校验和端口归属校验，避免误杀和孤儿进程。
3. **代理行为可控**：让上游代理配置显式可见；空值时不隐式继承环境或系统代理。
4. **配置可靠性**：增加配置 revision、重复端口校验、代理 URL 校验和写入冲突处理。
5. **规则管理能力**：增加描述、非法正则校验、重置、导出、导入和“待重启”状态。
6. **控制台使用体验**：补充生命周期控制、离线状态、更新错误本地化、管理令牌持久化和旧请求取消。
7. **看板口径**：明确缓存范围、统计单位、数据覆盖和指标含义，减少误读。
8. **载荷完整性**：保护 Base64、data URL 和多模态载荷，避免脱敏规则破坏二进制内容。
9. **管理认证兼容**：兼容 `x-dgw-admin-token` 和 Bearer，同时保留本地管理令牌流程。
10. **可维护性**：增加发布脚本、release skill、插件版本同步、本地规则样例、测试规则与 RMB 3.0 脱敏资料。

上游 `yuan-veil` 的 `v0.3.14` 对应提交 `f7e52ed`。本地正式版本提交为 `36b4021`，提交说明为“feat: 发布 Veil v0.3.14 正式版本”。

本地 tag `v0.3.14` 最终指向 `8989a5c`，因此记录时必须区分：

- `36b4021` 中包含的本地初始强化；
- `8989a5c` 及其后属于后续维护的内容；

这种区分很重要，否则容易把本地 `v0.3.14` 已经具备的增强误判为 `v0.3.15` 之后才出现，也容易把上游后续新增能力误认为本地已有。

### 2. 本地 v0.3.14 初始强化

这一轮强化发生在本地 `v0.3.14` 基线中，是后续本地版本的基础。

#### 2.1 控制面与转发数据面分离

新增 `crates/veil/src/lifecycle.rs`，把管理控制面与转发数据面拆成独立生命周期：

- 管理控制台常驻；
- 转发数据面可以单独启动、停止和重启；
- 停止或重启转发不需要退出整个 Veil；
- 退出 Veil 时会同时停止数据面和控制面。

新增或强化生命周期 API：

- `GET /api/lifecycle`
- `POST /api/lifecycle/start`
- `POST /api/lifecycle/stop`
- `POST /api/lifecycle/restart`
- `POST /api/lifecycle/exit`

控制台看板增加启动、停止、重启和退出入口，并展示控制面状态、转发状态、监听端口、PID、实例 ID 和最近错误。

解决的问题：原先网页只能查看状态，修改端口或上游后只能依赖命令行重启整个进程；停止、重启和故障诊断不可见，容易产生“配置已改但实际监听没变”的误解。

#### 2.2 上游代理可控化

配置中加入 `upstream_proxy`：

- 空值表示强制直连，不隐式继承系统代理或环境变量代理；
- 非空值必须是带主机的 `http` 或 `https` URL；
- 上游代理由配置显式决定，不再由进程启动时的系统环境被动决定。

解决的问题：旧行为可能隐式使用失效的系统代理或环境变量代理，导致所有上游请求统一失败，但控制台只看到 `upstream error`，难以定位。

影响范围：`crates/veil/src/config.rs`、`crates/veil/src/proxy/forward.rs`、管理 API 和控制台上游页面。

兼容性说明：空值行为与上游 `v0.4.x` 的直连意图接近，但配置字段和实现位置不同。上游支持通过 `[egress]` 配置代理，并包含 SOCKS5 设计；当前本地校验只接受 `http`/`https`，后续评估 SOCKS5 时需要调整配置模型和校验逻辑，不能直接复制上游实现。

#### 2.3 配置 revision 与校验

配置增加 `revision`，关键写操作需要提交预期 revision：

- 规则、白名单、上游或路由配置发生变化后递增 revision；
- 旧页面或并发请求使用过期 revision 时返回 `409`；
- 前端收到冲突后提示刷新，避免静默覆盖他人修改。

同时增加：

- 非法上游代理 URL 校验；
- 监听端口重复校验；
- 对 `proxy_port`、`management_port` 和客户端路由端口做冲突检查；
- `graceful_shutdown_timeout_secs`，限制数据面优雅停止的等待时间。

解决的问题：多个浏览器标签页、并发保存和手工编辑配置文件可能导致“最后保存者覆盖前一次修改”；错误端口或错误代理地址原先可能到转发时才暴露。

#### 2.4 单实例、运行元数据和进程安全

对 `crates/veil/src/process.rs` 和启动流程进行强化：

- 使用操作系统级单实例锁，锁由进程异常退出时自动释放；
- 运行元数据记录 PID、进程启动时间、实例 ID、可执行文件路径、管理端口、监听端口和转发状态；
- 启动和停止时校验进程启动时间、实例 ID、可执行文件路径和端口归属；
- 只有全部身份条件确认属于当前实例时，才允许自动终止进程；
- 清理 stale metadata 时不能仅凭进程名或端口直接杀进程。

解决的问题：重复双击、前台进程崩溃、程序重新编译或 stale PID 文件可能导致重复实例、端口占用或孤儿进程；旧的“按进程名停止”存在误杀其他程序的风险。

影响范围：启动、停止、状态查询、生命周期控制器、运行元数据、Windows 端口归属查询和控制台故障提示。

兼容性说明：这是本地最核心、也是最容易与上游冲突的一组改动。上游 `v0.4.1` 的 `main.rs`、认证和代理代码与本地差异较大。后续同步时应逐块移植，不应整文件覆盖。

#### 2.5 控制台状态与离线体验

控制台增加：

- 生命周期状态轮询；
- 数据面停止时仍可访问管理页；
- Veil 完全退出后的只读离线页；
- “待重启”提示和重启转发入口；
- 管理接口不可达时的明确错误状态。

解决的问题：关闭或重启数据面后，页面不能再用首次加载的“运行中”状态误导用户；用户需要知道控制面是否仍可访问、转发是否已停止、当前地址和端口是什么。

#### 2.6 配套测试与文档

本地 `v0.3.14` 基线还包含：

- 代理 URL、重复端口和配置 revision 相关测试；
- 生命周期启动、停止、重启和绑定失败回滚测试；
- 运行元数据 roundtrip 和单实例锁测试；
- 管理 API 生命周期写操作鉴权测试；
- `LAUNCH.md`、生命周期设计文档、发布说明和 UI 测试。

这些内容为后续规则管理和管理令牌改动提供了回归基础。

这是本地 `v0.3.16` 的核心功能。

变更内容：

1. **非法正则不再在加载时 panic**
   - `Rule::try_regex` 返回 `Result`；
   - 保留一个内部安全包装供内置规则使用；
   - 保存和加载配置时统一返回可读错误。

2. **从配置构建规则集**
   - `ruleset_from_config(&Config)` 根据当前配置动态构建 `RuleSet`；
   - 内置配置、启停状态、优先级、正则、词表、描述和白名单都参与构建；
   - 配置错误在启动转发或保存规则时返回，不替换当前有效配置。

3. **规则保存前校验**
   - 管理 API 收到非法规则时返回 `400`；
   - 不会把非法正则写入配置；
   - 避免运行中的数据面因坏配置崩溃。

4. **重置规则**
   - 清空自定义规则；
   - 恢复内置规则和默认白名单；
   - 前端增加确认提示。

5. **导出自定义规则**
   - 导出为 `veil-custom-rules.json`；
   - 只包含 `source=custom` 的规则；
   - 内置规则不进入导出文件。

6. **导入自定义规则**
   - 支持规则数组；
   - 支持 `{ "version": 1, "rules": [...] }`；
   - 导入时只替换 custom 规则，保留 builtin 规则；
   - 导入前执行结构、正则和必填字段校验。

7. **配置 revision 冲突控制**
   - 规则和白名单写操作携带 revision；
   - 过期写入返回 `409`；
   - 前端提示配置已变化并刷新，避免旧页面覆盖新配置。

8. **待重启标记**
   - 规则、白名单或上游配置变化后，生命周期状态标记 `pending_config_change`；
   - 控制台在“重启转发”按钮上显示提示；
   - 数据面继续使用启动时加载的旧规则，直到重启转发。

解决的问题：

- 用户改错正则后可能导致服务启动失败或运行异常；
- 手工维护 JSON/TOML 容易漏掉内置规则；
- 规则导入导出缺少边界，可能覆盖不应修改的 builtin 规则；
- 多标签页保存可能静默覆盖配置；
- 保存成功后用户不知道新规则是否已生效。

影响模块：

- `crates/veil-engine/src/rules.rs`
- `crates/veil/src/admin/api.rs`
- `crates/veil/src/admin/mod.rs`
- `crates/veil/src/config.rs`
- `crates/veil/src/lifecycle.rs`
- `crates/veil/src/proxy/forward.rs`
- `crates/veil/src/proxy/mod.rs`
- `ui/src/api.ts`
- `ui/src/i18n.tsx`
- `ui/src/pages/Rules.tsx`
- `ui/src/style.css`
- `迭代/202610` 下的规则样例和测试资料

运行时语义：

- 配置为空时使用内置默认规则；
- 配置中有规则时，使用配置中的完整规则列表；
- 保存规则不会自动热更新正在运行的转发数据面；
- 必须点击“重启转发”或先停止再启动；
- 如果转发已经停止，下次启动会读取最新配置。

兼容性：

- 新增 `description`、导入格式和 reset/export/import API 都是向后兼容扩展；
- 规则写入前会做更严格校验，非法正则从“可能 panic”变为“返回错误”，这是有意的行为变化；
- 当前“待重启”语义要求用户显式操作，不引入后台自动热重载。

需要评估的差异：上游 `v0.4.x` 将规则集构建移到 `crates/veil/src/ruleset.rs`，并加入 region pack。本地当前没有该文件，规则构建仍在 `proxy/forward.rs`。后续同步时应把“模块化”和“region pack 语义”分开评估，避免直接覆盖本地 `ruleset_from_config`。

#### 5.1 控制台管理令牌持久化

提交：`6154427 fix(console): 控制台地址带管理令牌，令牌改用 localStorage 持久化`

变更内容：

- 启动和 `veil ui` 输出的控制台地址携带 `?token=`；
- 前端首次打开控制台时可以从 URL 读取令牌；
- 管理令牌从 `sessionStorage` 改为 `localStorage`；
- 启动时自动迁移旧的 sessionStorage 令牌；
- 新标签页或重开浏览器后，保存上游、重启转发等写操作不再返回 `401`。

解决的问题：

- 管理令牌原先只存在于当前会话，新标签页或重开浏览器后丢失；
- 页面能打开，但写操作因缺少令牌失败，容易被误判为后端鉴权故障；
- 启动时自动打开的控制台无法可靠地完成首次令牌注入。

影响模块：`crates/veil/src/main.rs`、`ui/src/App.tsx`、`ui/src/api.ts`、`ui/src/i18n.tsx`。

收益：

- 改善本机使用体验；
- 减少重复输入令牌；
- 与本地生命周期 API 的写操作保护匹配。

风险与边界：

- `?token=` 可能出现在浏览器历史、地址栏复制内容或本地调试日志中；
- `localStorage` 在同一浏览器源下长期存在；
- 默认仅绑定 `127.0.0.1` 时风险较低，但如果把管理端口暴露到局域网或更换为非可信环境，需要重新评估；
- 当前实现与本地上游 `v0.4.1` 的登录页、Bearer/cookie 鉴权方向不同，后续同步时必须先做认证方案取舍，不能同时保留两套互相冲突的令牌入口。

后续改进候选：

- 认真评估上游登录页和 cookie/Bearer 鉴权，考虑是否用一次性 URL bootstrap 替代长期把令牌放在查询参数中；
- 增加“清除已保存令牌”的明确入口；
- 在非 localhost 绑定场景增加安全提示或禁止隐式持久化。

### 8. 对现有逻辑的影响评估

这里的“评估”不等同于“确定合入”，而是为后续同步提供判断依据。

#### 8.1 建议继续保留的本地能力

- 生命周期控制和进程安全清理；
- 配置 revision 和写入冲突检查；
- 规则描述、重置、导出、导入和非法正则校验；
- 显式 `upstream_proxy` 与空值直连语义；
- 看板缓存口径、数据覆盖提示和旧请求取消；
- Base64/data URL 与多模态载荷保护；
- 发布脚本、插件版本同步和本地规则资料。

原因：这些能力直接服务于本地的可维护性、安全性和可控性，且已经形成本地测试和文档基础。

#### 8.2 需要优先评估的上游能力

1. **base64/data URL 完整性保护**
   - 关注点：多模态请求中的图片、音频或其他二进制内容不应被普通敏感规则改写；
   - 风险：已通过结构校验、普通文本反例和代理回归测试控制；
   - 结论：P0 已实现，Base64 内容保持不变，普通文本仍继续扫描。

2. **Bearer/cookie 与管理令牌的统一**
   - 关注点：本地 `localStorage + ?token=` 与上游登录页/cookie/Bearer 会不会形成双重入口；
   - 风险：已通过认证优先级、错误令牌和 401 回归测试控制；
   - 结论：P1 已实现 `x-dgw-admin-token` 和 Bearer 头兼容；登录页/Cookie 未引入。

3. **egress proxy 与 `upstream_proxy` 合并**
   - 关注点：字段名、空值语义、http/https/SOCKS5 支持、管理流量是否直连；
   - 风险：不同默认行为会导致转发链路静默变化；
   - 建议：P2 暂不实施；未来先定义统一配置模型，再迁移代码。

4. **ruleset 模块化和 region pack**
   - 关注点：本地 `ruleset_from_config`、规则导入导出、revision 与上游模块化规则集如何整合；
   - 风险：正则校验、内置规则覆盖和配置回退语义可能改变；
   - 建议：P2 暂不实施；先建立规则加载回归矩阵，再考虑重构。

5. **Accept-Language 与 anti-ban 策略**
   - 关注点：这是对上游请求语义和产品定位的变更，不只是普通规则；
   - 风险：默认重写可能影响某些上游、调试结果或用户预期；
   - 建议：P2 暂不实施；未来只作为显式开关评估，不默认合入。

#### 8.3 不建议直接执行的操作

- 不直接执行 `git merge` 或整分支复制上游 `v0.4.1`；
- 不用上游 `main.rs`、`admin/auth.rs`、`proxy/forward.rs` 覆盖本地文件；

### 9. 兼容性与生效语义

#### 9.1 配置兼容性

- `description` 是可选字段，旧配置可以读取；
- 规则导入支持数组和带 `version` 的对象格式；
- 非法正则不再触发 panic，而是返回错误；
- `upstream_proxy` 当前只接受 `http`/`https` URL；
- 配置 revision 是本地并发控制字段，旧客户端不提交 revision 时需要确认 API 兼容策略；
- 版本升级不自动迁移数据目录中的原文件。

#### 9.2 数据面生效语义

- 转发数据面在启动或重启时构建并持有规则集；
- 规则、白名单或上游配置保存后，不会自动影响正在运行的转发；
- 状态显示 `pending_config_change=true` 时，必须重启转发；
- 停止状态下再次启动会读取最新配置；
- 生命周期重启只重建数据面，不要求退出管理控制台。
- 被识别为 Base64 / data URL 的二进制内容不进入普通规则扫描，原样转发；其他字符串继续按现有规则扫描。

#### 9.3 管理令牌与浏览器

- 服务端保存的是令牌哈希，明文令牌文件位于数据目录；
- 控制台写操作需要管理令牌；
- 当前启动地址可能带 `?token=`；
- 当前浏览器令牌使用 `localStorage`，并支持从旧 `sessionStorage` 迁移；
- 如果管理端口暴露到不可信网络，现有持久化方案需要重新评估。
- 管理 API 接受 `x-veil-admin-token`、`x-dgw-admin-token`、`Authorization: Bearer <token>` 以及现有 Cookie；认证优先级按实现执行。
