# rmb_3.0 项目专属脱敏配置与 Veil 适配方案

> 日期：2026-10-10  
> 状态：方案草案，未实施，候选规则未经端到端验证  
> 适用对象：rmb_3.0 开发、运维及 Veil 维护人员  
> 目标项目：`D:\workspace\cnb\rmb_3.0`  
> 配置载体：Veil 本地代理；不是给各业务服务安装脱敏组件

## 1. 目标与边界

rmb_3.0 是包含多个后端模块、多个前端工程的业务项目。开发人员使用 AI 阅读配置、分析日志、排查接口错误时，可能将凭据、个人信息、企业基础设施信息一同发送给外部模型。

本方案分成两个部分：

1. **项目规则设计**：基于实际配置和代码形态，补充 rmb_3.0 特有的敏感信息识别规则。
2. **Veil 必要适配**：让控制台保存的规则真正应用到代理转发，并提供项目配置隔离和本地验证能力。

不需要为每个后端或前端服务分别部署 Veil。首先保护开发人员使用的 AI 客户端；只有需要保护业务服务自身发起的模型调用时，才另行评估服务端接入。

### 1.1 保护范围

- 经过 Veil 的模型请求 body 中的文本，包括用户粘贴的配置、日志及客户端发送的工具结果。
- 同一敏感值保持一致别名，尽量保留排障中的关联关系。
- 上游响应中的已知别名由 Veil 还原，再返回客户端。

### 1.2 不属于本方案的保证

- 不自动扫描并改写整个 rmb_3.0 仓库，不承担 Git 提交前检查。
- 不保护绕过 Veil 的客户端、上传链路或业务请求。
- 不把 API 鉴权头中的凭据替换成别名，否则可能破坏正常登录和调用。
- 文本规则不能保证识别图片、PDF 扫描件、二进制证书及编码后的附件。
- 不自动修复已经提交到 Git 的凭据，也不能撤回已发送到外部服务的数据。
- 正则识别存在漏报和误报，不能把“没有命中”解释为“已经证明安全”。

## 2. 项目扫描摘要

本次进行了结构、配置、部署文件、部分鉴权与日志代码的抽查，不是完整安全审计；未连接数据库、云服务或验证任何凭据的有效性。文档不记录真实密钥值。

### 2.1 工程特点

| 范围 | 观察到的结构 | 对脱敏适配的影响 |
|---|---|---|
| `backend/` | Kotlin/Java、Gradle 多模块、Spring Boot/Spring Cloud；构建包含 22 个模块，找到 15 个 Spring 应用入口 | 不应将模块数等同于部署服务数；配置格式重点覆盖 YAML、Kotlin/Java、XML |
| 后端依赖 | MySQL、Redis、Elasticsearch、Nacos、OSS、支付、短信、推送、外部接口 | 凭据不只有 `password` 或 `api_key`，存在大量业务特有字段 |
| `frontend/` | 多个 Vue 3/Vite/uni-app 工程，包含 Web、App/H5/小程序等形态 | 关注 `.env.*`、`manifest.json`、接口配置及浏览器登录态 |
| `devops/`、`test/` | 部署 YAML、构建参数、Playwright 登录状态 | 不能只扫描 backend/frontend，也不能只保护生产环境配置 |

### 2.2 建议重点保护的文件

以下路径均相对于 rmb_3.0 项目根目录：

- `backend/application-prod-yaml/*.yaml`。
- 各模块的 `src/main/resources/application*.yaml`、`bootstrap.yaml`、`log4j2-*.xml`。
- `backend/build.gradle.kts` 及模块构建脚本。
- 支付、用户、推送、极光、物流 CDS、商城等模块的第三方接口配置。
- 前端 `.env.dev/.test/.uat/.prod`、`manifest.json`、地图及接口配置。
- `test/**/.auth/*.json`、`test/**/storage/auth.json` 等登录状态文件。
- `devops/` 下的部署文件和启动参数。

环境名为 dev/test 不代表其中的凭据无害；开发配置也可能使用真实云密钥或支付凭据。

## 3. 必须先确认的 Veil 现状

### 3.1 自定义配置目前没有接入代理运行链路

核对当前工作区源码发现：

| 项目 | 当前实现 | 方案影响 |
|---|---|---|
| 代理规则初始化 | `crates/veil/src/proxy/forward.rs:58` 固定使用 `builtin_ruleset()` | 控制台保存自定义规则不代表转发时使用了这些规则 |
| 规则保存 | `crates/veil/src/admin/api.rs:207–228` 全量保存 `cfg.rules` | 保存成功只能证明配置落盘，不能证明生效 |
| 允许列表 | 配置可以保存，但上述代理规则仍使用内置允许列表 | 自定义允许列表同样不能按已生效处理 |
| 项目选择 | `Config` 中规则为实例级配置，route 没有规则包字段 | 当前不能依据工作目录或客户端 route 自动选择项目规则 |
| 新增规则界面 | `ui/src/pages/Rules.tsx:73–85` 仅新增 regex，初始优先级为 50 | 新增后需要编辑优先级；不能宣称界面支持直接新建 dictionary |
| 词典能力 | 引擎支持 dictionary，配置支持 `words`，界面可编辑已有词典 | 还需要配置到运行时的转换，以及可用的新增入口 |
| 本地测试 | 没有现成的规则 dry-run HTTP 接口或 CLI 子命令 | 不能把文档中的测试步骤写成已经存在的产品功能 |

**结论：本方案中的新增规则目前是待落地配置设计。必须先修复规则接入，再验证实际转发。仅重启当前源码对应的程序不会自动补齐这条链路。**

如果使用的是另一版本的已发布 exe，应单独核对版本和运行效果，不能直接把当前工作区源码结论等同于所有发布版本。

### 3.2 需要修正的使用预期

- Traffic 页面记录请求状态、命中类型等摘要，不展示请求原文或具体占位符。
- 客户端收到明文可能是正常还原的结果，不能据此判定上游有没有收到明文。
- 自定义正则中 `|` 是分支运算符；复制 Markdown 表格时不能误用 `\|`，后者匹配的是字面竖线。
- 现有正则引擎替换的是**完整匹配片段**，不是某个捕获组。匹配 `appSecret: value` 会连字段名一起替换，不能宣称已经保留了字段结构。
- 内置 JWT 正则只覆盖部分 JWT 形态，完整原始 JWT 应增加独立测试；不能只因为存在 `eyJ` 规则就认为签名段一定全部被遮盖。
- 允许列表按**完整命中字符串精确比较**，不支持目录排除或通配符，也不是“这个字段下面都不脱敏”。

## 4. 项目规则分层

### 4.1 第一层：凭据保护，默认开启

| 类别 | rmb_3.0 中的特征 | 适配建议 |
|---|---|---|
| 数据库/中间件 | JDBC 地址、数据库/Redis/ES/Nacos 密码 | 保留内置连接串和密码规则，补充短口令、JSON 引号及多种配置语法测试 |
| 阿里云 AK/SK | `LTAI…`；`accessKeyId/accessKeySecret`；嵌套 `access_key.id/secret` | 增加 LTAI 前缀规则；嵌套字段用上下文处理，不全局匹配 `id` |
| JWT | 原始 `eyJ….….…`，不一定带 Bearer | 匹配完整三段及签名；覆盖网关日志、Header 文本和浏览器状态 |
| JWT 签名密钥 | `jwt.secret`；YAML 中 `jwt:` 下的 `secret:` | 使用字段路径/上下文规则，不能依赖高熵判断 |
| 微信支付/汇付 | `apiV3Key`、`privateKey`、`rmbPrivateKey`、PEM 或裸 Base64 | 先覆盖单行字段；多行 YAML 私钥需专门解析和测试 |
| AI/工作流 | `sk-…`、Coze `sat_…` | 保留 sk 前缀识别，增加 sat 前缀规则 |
| 飞书/企微/极光 | `appSecret`、`corpSecret`、`masterSecret`、`encodingAesKey` | 统一 camelCase、snake_case、kebab-case 字段变体 |
| 地图/OCR/隐私通话 | `GAODE_MAP_API_KEY`、`securityJsCode`、UUID 形 `private-key` | 按字段名识别，不把所有 UUID 或 32 位 hex 都认作秘密 |
| 构建与仓库 | `repositoryPassword`、`jib_password`、`nacos_secret_key` | 覆盖构建赋值、命令行 `-Dname=value` 及脚本参数 |
| URL/接口日志 | 微信 URL 中的 `secret/js_code/access_token`，`Authorization: APPCODE …` | 处理请求 body 内的 URL/日志文本；不修改模型请求自身的鉴权头 |

### 4.2 第二层：个人与资金信息，分项开启

- 手机号、身份证：保留内置规则。
- 银行卡、资金账号、支付关联账号：结合 `bankCardNo`、`merAcctNo`、`serviceFundAccount` 等字段名识别。
- 微信 `openid/unionid`、用户和 profile 标识：采用字段上下文规则。
- 姓名、企业联系人：不建议仅凭两三个汉字的正则强制遮盖，应结合字段名或经批准的本地词表。
- 保留 trace ID、请求 ID 等排障信息，除非它们直接包含个人信息。

不要全局匹配所有数字、UUID、`id`、`key` 或长 Base64。否则订单 ID、代码、公钥和日志关联信息都可能被误伤。

### 4.3 第三层：企业信息，默认关闭

可选内容包括：

- 企业域名后缀：`rongmeibao.com`、`rongtongkeji.com`、`teamy.cn`、`rmuu.cn`。
- 已确认归属本企业的 RDS、Nacos、OSS 实例域名。
- 数据库命名、Nacos namespace、镜像仓库路径。
- 企业名称、项目代号、内部客户或商户标识。

不建议遮盖所有 `aliyuncs.com` 域名，也不建议全局遮盖 `RMB`、`teamy` 或所有服务名。`RMB` 还可能表示人民币，`teamy` 可能出现在包名、Header 和文件路径中。

日常代码分析优先保留模块名、类名和接口路径；面向外部分享配置时，再启用企业信息模式。

## 5. 第一批候选规则

以下是面向当前 fancy_regex 引擎的**候选模式**，不是已验证配置包。优先级越大越先匹配；高优先级占用的片段不会再次被低优先级规则替换。

现有参考优先级：PEM 220、API Key 210、Token 205、连接串 180、密码 170、身份证 150、手机号 140、IP 120。

### 5.1 阿里云 AK

- ID：`rmb_aliyun_ak`
- 前缀：`ALIYUNAK`
- 优先级：215
- 默认开启。

```regex
(?<![A-Za-z0-9_])LTAI[A-Za-z0-9]{12,28}(?![A-Za-z0-9_])
```

覆盖观察到的新旧 LTAI 形态；长度范围需要通过匿名化样本确认，AK 对应的 SK 则必须另行按字段识别。

### 5.2 完整原始 JWT

- ID：`rmb_jwt_full`
- 前缀：`TOKEN`
- 优先级：216，高于内置 token 规则，避免先命中不完整片段。
- 默认开启。

```regex
(?<![A-Za-z0-9_-])eyJ[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+(?![A-Za-z0-9_-])
```

适用于常见三段式签名 JWT，不承诺覆盖五段 JWE、截断 token 或所有非标准格式。

### 5.3 Coze token

- ID：`rmb_coze_token`
- 前缀：`TOKEN`
- 优先级：215
- 默认开启。

```regex
(?<![A-Za-z0-9_])sat_[A-Za-z0-9_-]{20,}(?![A-Za-z0-9_-])
```

### 5.4 项目特有单行凭据字段

- ID：`rmb_secret_field_line`
- 前缀：`SECRET`
- 优先级：230，优先处理完整赋值，避免值中的 sk 前缀等先占用片段。
- 默认开启，但需要较完整的误报测试。

```regex
(?i)(?<![A-Za-z0-9_])["']?(?:app[_-]?secret|corp[_-]?secret|master[_-]?secret|access[_-]?key[_-]?secret|secret[_-]?key|api[_-]?v3[_-]?key|encoding[_-]?aes[_-]?key|security[_-]?js[_-]?code|a[_-]?map[_-]?security[_-]?js[_-]?code|rmb[_-]?private[_-]?key|private[_-]?key|repository[_-]?password|jib[_-]?password|nacos[_-]?secret[_-]?key|gaode[_-]?map[_-]?api[_-]?key)["']?\s*[:=][ \t]*(?:"[^"\r\n]+"|'[^'\r\n]+'|[^\s,;#&<>"']+)
```

注意：

- 该模式替换**整个赋值片段**，不是仅替换值。适合临时保护，不是最终结构保留方案。
- 不覆盖 YAML `|`/`>` 多行值、XML 元素、Kotlin 的 `private val …: String = …` 等所有语法。
- `${VARIABLE}` 环境变量引用可能被整体命中；它未必包含真实秘密。解析型规则应区分空引用和携带敏感默认值的引用。
- 裸 `secret:`、裸 `token:` 和嵌套 `access_key.id` 没有在此无条件匹配，应由上下文能力补充。

### 5.5 URL 查询参数中的凭据

- ID：`rmb_url_secret`
- 前缀：`URLSECRET`
- 优先级：235
- 默认开启。

```regex
(?i)(?<=[?&])(?:access[_-]?token|refresh[_-]?token|secret|app[_-]?secret|js_code|signature)=[^&\s"'<>#]+
```

保留前面的 `?`/`&`，但当前会替换 `参数名=值` 整体。`appid` 通常是应用标识，不与 secret 混为一谈；确需隐藏时放入企业标识规则。

该规则只针对 body 文本中的 URL，不等于 Veil 会改写实际请求 URL 查询参数。

### 5.6 APPCODE 鉴权日志

- ID：`rmb_appcode`
- 前缀：`TOKEN`
- 优先级：215
- 默认开启。

```regex
(?i)\bAPPCODE[ \t]+[A-Za-z0-9_-]{8,}
```

仅处理作为文本发送给模型的鉴权信息。

### 5.7 企业域名与数据库名，可选

企业域名，ID `rmb_corp_domain`，前缀 `CORPDOMAIN`，优先级 110：

```regex
(?i)(?<![A-Za-z0-9_.-])(?:[a-z0-9-]+\.)*(?:rongmeibao\.com|rongtongkeji\.com|teamy\.cn|rmuu\.cn)(?![A-Za-z0-9_.-])
```

数据库名，ID `rmb_db_name`，前缀 `DBNAME`，优先级 100：

```regex
\brmb_2_(?:user|trade|logistics)_(?:test|prod)(?:_new)?\b
```

两者均默认关闭。连接串内的域名和库名若已整体被 CONNSTR 规则匹配，不需要再次拆分替换。数据库名模式也不代表覆盖所有实际库名。

## 6. Veil 必要适配项

### 6.1 P0：让保存的规则真正生效

建议先完成以下最小闭环：

1. 建立唯一的 `Config → RuleSet` 转换入口，代理和管理页面使用一致语义。
2. 配置为空时使用内置规则；配置非空时，明确是否为“完整有效列表”，避免隐式丢失内置保护。
3. 按现有全量保存界面设计，优先明确采用“完整有效列表”：首次编辑以完整内置列表为基础，修改其属性并追加自定义项。
4. 内置 IP 规则必须保留解析式 matcher，不能因没有 pattern 被误当作空正则。
5. 转换 `words` 为 dictionary，应用配置中的 allowlist；对重复 ID、空模式、非法正则及非法前缀进行验证。
6. 保存前构建候选规则集，验证成功后再持久化和切换；失败不能留下部分生效状态。
7. 默认代理端口与各 route 共享同一有效规则版本，明确采用热更新还是重启生效。
8. 控制台显示“保存版本”和“实际生效版本”，不要仅以保存成功提示代表生效。

候选规则及既有内置规则的匹配异常策略也应明确。当前引擎的部分正则错误会作为该规则未命中处理，不应据此宣称所有无法确认安全的文本都会被阻断。

### 6.2 P1：值级别与上下文识别

目标是保留字段名、引号和配置结构，只替换敏感值，例如：

```yaml
jwt:
  secret: "{{SECRET_示意别名}}"

wechat:
  apiV3Key: "{{SECRET_另一示意别名}}"
```

上面的别名仅为文档示意，不是实际 ULID 格式。

建议能力：

- 正则支持显式选择 value 捕获组的替换范围，并保持现有完整匹配模式的兼容性。
- 对 JSON 文本对象和 YAML 配置内容提供字段路径识别，例如 `jwt.secret`、`access_key.secret`。
- 区分模型协议外层 JSON 与其中作为字符串出现的配置文本；仅递归扫描 JSON 字符串不足以获得业务配置字段上下文。
- 覆盖 YAML 多行裸 Base64 私钥、XML 配置、环境变量默认值及常见命令行形式。
- 不全局匹配 `id/key/secret/token` 等模糊字段，不改变业务应用的登录凭据。

### 6.3 P1：本地规则验证

增加本地测试入口，用合成样本展示：命中规则、替换范围、命中类型和脱敏结果。

- 默认不写入生产映射表；需要别名演示时使用临时映射。
- 不把测试输入发给任何远程模型。
- 不保存真实输入到日志、遥测或可导出的测试报告。
- 输出“未命中”时提醒仍可能存在漏报，不给出绝对安全结论。

### 6.4 P2：项目配置包与选择机制

建议设计可导入/导出的 `rmb_3.0` 规则包，包含规则、开关、描述、优先级、版本和合成测试样本，不包含真实密钥。

后续可提供显式 profile 或 route 绑定；工作目录只能作为客户端提供的选择信号，不能假设 HTTP 代理天然知道当前仓库路径。没有可靠选择信息时，不应静默关闭凭据保护。

## 7. 项目隔离的落地方式

### 7.1 第一阶段优先使用独立实例

在 P0 完成后，可为 rmb_3.0 使用独立数据目录和端口，隔离规则、映射、管理 token 与生命周期文件，避免切换项目时污染其他项目配置。

当前的数据目录支持 `VEIL_DATA_DIR`；并没有 `--data-dir`、`--proxy-port` 等启动参数。端口应在独立目录的 `config.toml` 中配置。

示例最小配置，**不是完整生产配置，也不包含规则包**：

```toml
bind = "127.0.0.1"
proxy_port = 19787
management_port = 19788
routes = []
```

PowerShell 启动示意：

```powershell
# 仅在为该实例使用的终端中设置，避免改变其他 Veil 操作的目标目录。
$env:VEIL_DATA_DIR = Join-Path $env:LOCALAPPDATA 'veil-rmb3'

# 先在此目录准备 config.toml，并确认端口未被占用。
# 替换为实际 exe 路径；此处不自动切换任何 AI 客户端。
& 'C:\实际安装目录\veil.exe' start --foreground
```

注意事项：

- 应根据现有客户端所用上游配置该实例，不要用示例默认值覆盖公司的中转地址。
- 如果使用 routes，其端口也必须避开其他实例。
- 独立实例不能自动补齐 P0；在当前规则接入缺失的源码中，独立启动仍只使用内置规则。
- 更改 AI 客户端 Base URL 属于另一步操作，应由开发人员明确选择；避免通用 setup 改到不相关客户端。
- 映射数据库、主密钥和管理 token 不应放入业务仓库，也不应随规则包导出。

### 7.2 不建议按每个服务分别建规则包

后端与前端共享很多凭据类型。第一阶段采用“项目公共凭据规则 + 可选个人/企业信息规则”即可。

只有实际发现某类规则严重误伤某个客户端用途，或不同团队确有不同策略时，再增加子配置。避免一开始维护几十份近似规则。

## 8. 允许列表策略

保留默认回环地址：`127.0.0.1`、`localhost`、`0.0.0.0`、`::1`。

新增允许项需要满足：

1. 是确定无敏感性的测试值或误报值。
2. 与实际命中片段完全一致。
3. 具有可复现的误报样例和添加原因。

不应允许：生产/测试真实口令、默认弱口令、真实云密钥、真实手机号或“整个企业网段”。

服务名通常不会被默认规则匹配，无需为了“保留服务名”机械加入允许列表。`x-teamy-trace-id` 字段名本身也无需放行；是否命中取决于其实际值。

## 9. 验证与验收

所有样本必须合成或充分匿名化；不把真实生产配置发送给模型做验证。

### 9.1 匹配测试矩阵

| 场景 | 应验证的结果 |
|---|---|
| 合成 LTAI、sat、完整 JWT | 整个秘密被遮盖，尤其 JWT 签名段不能残留 |
| 无 Bearer 的 JWT 日志 | 仍命中 TOKEN |
| camelCase/snake_case/kebab-case 凭据字段 | 同一类规则覆盖约定的变体 |
| JSON 带引号、YAML 单行、多行私钥、XML | 分别测试；不把单行通过等同于所有语法通过 |
| 微信 query、APPCODE、构建参数 | 覆盖请求 body 内的文本形式 |
| 短口令、UUID 形密钥 | 依字段上下文识别，而非仅依赖长度或熵 |
| 普通 UUID、订单 ID、公钥、trace ID、示例域名 | 不被无条件遮盖 |
| 相同秘密重复出现 | 在同一映射作用域内获得一致别名 |
| 私钥中含看似其他凭据的字符串 | 明确优先级和重叠处理，不留下私钥尾段 |
| 修改、关闭规则及允许列表 | 实际转发使用生效版本，而不只是控制台显示变化 |

### 9.2 代理端到端测试

使用本机 mock 上游捕获 Veil 实际发出的请求，参考 `crates/veil/tests/proxy_core.rs` 的测试方式：

1. 向 Veil 发送包含合成敏感值的请求。
2. 在 mock 接收端断言原始值不存在，预期类型别名存在。
3. mock 原样返回别名，验证客户端收到正确还原值。
4. 分别覆盖 JSON 和 SSE、不同客户端协议、默认端口和 route。
5. 保存规则后重复测试，证明运行规则已切换。

**客户端响应不出现占位符不能证明失败，出现明文也不能证明泄露；上游接收端的请求才是脱敏验证依据。**

### 9.3 验收门槛

- P0 规则接入问题已修复，配置版本与生效版本可核对。
- 本文第一批默认开启规则通过匿名样本与负例测试。
- 对 YAML 多行私钥、嵌套 secret 等未覆盖场景明确列出限制，不作虚假完成声明。
- 所有启用的规则均完成本地 mock 转发验证。
- 企业信息规则默认关闭，开启后不影响基本代码排障关系。
- 原有内置规则和其他客户端转发行为无回归。

## 10. 仓库凭据治理，独立于 Veil

抽查发现多类 Git 跟踪文件包含非空、看起来不像占位符的凭据，还存在被跟踪的证书和浏览器登录态。尚未验证其有效性，也不能仅凭文件名确认所有证书都有私钥。

建议由有权限的维护人员：

1. 建立凭据清单并确认环境、所有者和实际用途，不在普通文档中记录原始值。
2. 对确认已暴露或不符合存储规范的凭据制定轮换计划，避免直接操作导致服务中断。
3. 将服务端秘密迁移到环境变量、受控配置系统或密钥管理服务。
4. 停止跟踪本地登录状态和不应入库的私钥/证书，增加提交前及 CI secret scanning。
5. 需要清理 Git 历史时，另行审批并协调所有协作者；删掉当前文件并不等于历史消失。
6. 前端地图 Key 等可公开客户端标识应配合域名、包名、签名及配额限制，不能仅靠“隐藏字符串”实现安全。

Veil 是开发过程中向模型发送内容的最后一层保护，不能代替上述治理。

## 11. 推荐执行顺序

1. **先修复 Veil 配置到运行时的规则接入（P0）。**
2. 建立合成样本和 mock 上游测试，验证内置规则及完整 JWT 处理。
3. 接入 AK、Coze、项目字段、URL query、APPCODE 等第一批规则。
4. 补齐值级替换与 YAML/JSON 上下文能力，重点保护支付私钥和嵌套 secret。
5. 在独立实例中配置 rmb_3.0，明确选择需要接入的 AI 客户端。
6. 按需开启个人信息、企业域名和内部标识规则。
7. 增加规则包导入导出、本地测试界面和显式项目选择能力。
